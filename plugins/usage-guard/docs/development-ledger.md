## Post-ship production bug: probe recursion (2026-08-20/21)

Found by installing the plugin for real and watching it misbehave, not by review. Sixteen prior reviews (the task-by-task rounds and the whole-branch reviews below) missed it because each one saw a different edge of a cycle in isolation: the singleton lock was reviewed and hardened on its own merits (Task 9, two fix rounds), the SessionStart wiring that launches the poller was reviewed on its own merits (Task 10), and the most recent review correctly cleared the gate's relaunch throttle, a related but different code path. No review traced the full loop: poller runs `claude -p "/usage"` at hooks/usage-poller -> that starts a brand new Claude Code session -> the plugin's own SessionStart hook fires in that child session -> it launches another poller -> which probes -> which starts another session. Observed in production: 38 probes in 83 seconds, a new poller roughly every two seconds, unbounded. The singleton lock did not stop it, because each poller is short-lived; the next one always finds a dead owner pid, correctly declares the lock stale per its own (correct) design, reclaims it, and probes again. `guard.log` filled with "poll: reclaiming stale lock from pid NNNNN", a different pid every time. That log line is the fingerprint of the recursion, not evidence of a lock defect, which is part of why it read as healthy self-recovery rather than a runaway.

What kept this from being catastrophic rather than merely wasteful: `/usage` consumes no model turn, only a process spawn, so the storm cost process churn rather than the usage budget this plugin exists to protect. Any sensor command that did cost tokens would have drained the window in about two minutes, the exact disaster this plugin is built to prevent. This must not be relied on going forward; it is a property of `/usage` specifically, not of the design.

Fix, two layers. Layer 1: `USAGE_GUARD_PROBE=1` is exported onto the probe's own `claude -p "/usage"` invocation in `run_probe`, and usage-poller checks it as the very first line of the file, before sourcing anything and before any lock work, so a probe-launched session's poller does zero work: no lock acquisition, no log line, no state write. The same check was added to usage-gate near its existing `guard_disabled` check, exiting 0 emitting nothing: `/usage` issues no tool calls today so this path is not reachable yet, but if that ever changed, a frozen probe could never refresh the state it exists to produce, and the system would deadlock. Layer 2, a backstop for if the sentinel is ever lost: `probe_due` in lib/config.sh, built on the existing `stamp_due` helper (the same one `relaunch_due`, `gate_seen`, and `warn_due` use), caps probes to at most one per `PROBE_MIN_INTERVAL` seconds (default 30), machine-wide, independent of the sentinel. `run_probe` checks it before spawning the probe process. `PROBE_MIN_INTERVAL` is screened the same way as the other bash-arithmetic config values (leading zero and bare non-digit both reject to the default).

Tests added: test_poller.sh gets a true regression test that runs usage-poller as a real program (not sourced) with `USAGE_GUARD_PROBE=1` set and asserts exit 0, empty stdout, no lock directory, and no guard.log line, isolated into its own GUARD_DIR so it cannot pass by riding on a log file another assertion already populated; plus direct coverage of `probe_due` (fresh stamp, throttled stamp, stamp-before-return-so-two-same-second-callers can't both fire, and the older-than-interval case) and the `PROBE_MIN_INTERVAL` leading-zero/bare-zero screen. test_gate.sh gets a fabricated FREEZE-band state (99%, future reset) run with `USAGE_GUARD_PROBE=1` and asserts exit 0, zero stdout bytes, and that it returns immediately rather than entering the freeze wait, so the test would actually fail (or hang, bounded to a few seconds by a short fabricated reset) if the early exit were removed, rather than passing by accident because there was nothing to hold. 167 assertions total (153 pre-existing plus 14 new: 11 in test_poller.sh, 3 in test_gate.sh), 0 failed, verified across five consecutive `./test/run-tests` runs.

## Post-ship production bug: probe recursion, fix round 2 (2026-08-21)

Review of the recursion fix above confirmed the cycle is broken and found five further issues, committed separately from the recursion fix so each stays reviewable on its own.

Important, separate commit: `acquire_lock`/`own_lock` recorded and compared `$$`, which bash pins to the LAUNCHER's pid even inside the `main_loop &` backgrounded subshell the lock actually protects. The launcher exits within milliseconds of backgrounding, so the lock named an already-dead pid while the loop it guarded kept running; every later poller correctly found that pid dead and reclaimed a lock that was still legitimately held. This produces the exact same `guard.log` fingerprint ("poll: reclaiming stale lock from pid NNNNN", a fresh pid every time) as the probe-recursion storm, but is an independent bug that predates it and persists after the recursion fix. Switched both to `$BASHPID`. Regression test demonstrates the recorded pid is the backgrounded subshell's own live pid, not `$$`, without running a real `main_loop`.

Minor: the sentinel regression test originally awaited `usage-poller`'s stdout via command substitution; with the early exit removed (as verified by mutation testing it), `main_loop &` never closes that fd and the suite hung roughly ten minutes rather than failing. Rewrote it to background the invocation itself, poll `kill -0` for a bounded ~2 seconds, and assert on exit rather than on pipe EOF. Also put a stub `claude` on PATH for that one test block, so a reverted early exit cannot escalate to a real probe session even inside CI. Confirmed by mutation testing again post-fix: the removed-early-exit case now reports a named `FAIL` (caught by the "writes no lock directory" assertion) and completes in a couple of seconds, not a hang.

Minor, test-integrity: `test_poller.sh` dot-sources `usage-poller` with `POLLER_LIB_ONLY=1`, and `exit` inside a sourced file exits the SOURCING shell. The sentinel early exit could therefore have killed the whole test file (zero assertions printed) if the suite ever ran with `USAGE_GUARD_PROBE=1` already in the environment, and `run-tests` would have reported that as green since it counts printed lines rather than checking against an expected count. Guarded the early exit with `[ -z "${POLLER_LIB_ONLY:-}" ] && ...`. This is the fourth test-integrity hazard found on this project (see the ASSERT_TOTAL/ASSERT_FAILED dead-state note under Task 1, and the two greedy-regex/`head -1` notes under Tasks 2-4 and Task 8). Verified by sourcing the file directly with both variables set and confirming the sourcing shell survives.

Minor: `USAGE_GUARD_PROBE=1` silently disables both hooks with no trace anywhere. Added one `guard_log` line in `run_probe` recording that a marked probe session was launched (deliberately not on the gate side, since that path is unreachable while `/usage` issues no tool calls, and the gate's fast path is already the most latency-sensitive code in the plugin). Added `USAGE_GUARD_PROBE` to the README's environment table, marked internal/reserved/do-not-set, since it previously appeared only in prose.

Minor: a skipped probe (under `PROBE_MIN_INTERVAL`) still fell through to `read_cache`/`write_state_file` with a fresh `ts`, republishing the old cached reading as current and defeating `STALE_SECONDS` for that cycle; bounded to 30s at the default but unbounded if `PROBE_MIN_INTERVAL` is ever raised above `interval_for`'s tightest 120s poll. `run_probe` now returns 1 on skip (0 whenever it actually ran), and `poll_once` returns early without touching state when it does.
