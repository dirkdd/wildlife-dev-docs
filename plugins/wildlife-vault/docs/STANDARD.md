# The Vault Standard

A complete description of the agent-maintained knowledge vault: what each node type is for, the frontmatter contract, the relation grammar, the index system, and the enforcement model. This is the spec to read to understand the system end to end.

## 1. Purpose and shape

The vault is a small, typed, validated knowledge graph that lives in the repo at the path configured in `docs/vault/.vault.json` (default `docs/vault/Knowledge/`) and is maintained by the agent. It is Obsidian-compatible (wikilinks, frontmatter, graph view) and enforced by hooks and a validator so it cannot rot into freeform notes.

Every node is a Markdown file with YAML frontmatter (the contract) and a structured body. Nodes are connected by typed `rel_*` relations that render as edges in the Obsidian graph. Generated index files keep navigation cheap as the vault grows.

## 2. Node types

| type | folder | role |
|------|--------|------|
| concept | `concepts/` | a domain or technical concept |
| module | `modules/` | a code surface or feature area |
| flow | `flows/` | an end-to-end process across modules |
| data | `data/` | a data-shape or schema contract |
| invariant | `invariants/` | a rule that must hold + its failure mode |
| decision | `decisions/` | an ADR (architecture decision record) |
| runbook | `runbooks/` | an operational procedure |
| guide | `guides/` | a how-to or explanation |
| reference | `_meta/` | a pointer or schema doc |
| moc | `_meta/` | a map of content (index) |
| learning | `_meta/learnings/` | a generalizable insight captured to evolve the plugin |

## 3. The frontmatter contract

Required on every node:

- `id` — kebab-case, matches the filename without `.md`
- `title` — human-readable
- `type` — one of the types above
- `doc_class` — see doc_class enum below
- `summary` — one or two sentences; this is what indexes show and what other sessions read first
- `status` — `draft | canonical | stale | deprecated`
- `provenance` — `verified | extracted | inferred | ambiguous`
- `tags` — array; should include at least one `domain/*`, plus the `class/<doc_class>` mirror tag that drives the Obsidian graph colors
- `updated` — ISO date

Optional:

- `diataxis` — `tutorial | how-to | reference | explanation`
- `aliases` — array of alternative names (for the link scanner)
- `sources` — provenance pointers (PRDs, specs, external docs)
- `code_refs` — `path` or `path#symbol` references into the codebase
- `rel_*` — typed relations (see below)

`learning` nodes also carry `learning_kind` (`type | strategy | taxonomy | validation | technique`), `learning_status` (`proposed | harvested | adopted | rejected`), and `adopted_in`. See `docs/superpowers/specs/2026-05-30-vault-self-learning-design.md` for the self-learning loop.

## 4. Relations

All relations are flat top-level keys, lists of quoted wikilinks:

```yaml
rel_documents:
  - "[[some-id]]"
rel_depends_on:
  - "[[other-id]]"
```

The eight relation types:

- `rel_documents` — this node documents that one (e.g. a guide documents a module)
- `rel_depends_on` — this node depends on that one
- `rel_governed_by` — this node is governed by that rule/decision
- `rel_decided_in` — this node's existence/shape was decided in that ADR
- `rel_part_of` — this node is part of that larger thing
- `rel_related` — loose association
- `rel_supersedes` / `rel_superseded_by` — decision lineage (decision nodes only)

## 5. The index system

Three tiers, all generated by `/vault-map` (the `vault-map` skill):

1. **Router** (`_meta/index.md`) — the tier-0 entry point. Lists node types and links to sub-indexes. Read first.
2. **Sub-indexes** (`_meta/index-by-type.md`, `_meta/index-domain-*.md`) — group nodes by type and by domain.
3. **Node bodies** — the actual content, opened on demand.

The generated regions are wrapped in `<!-- vault-map:begin -->` / `<!-- vault-map:end -->` markers. Hand-written content outside those markers is preserved.

## 6. Enforcement

Three hooks (see the plugin's `hooks/hooks.json`), all resolved per-project and fail-safe no-op when the repo has no `docs/vault/.vault.json`:

- **PreToolUse** (Write|Edit) — validates a node *before* it lands; a hard violation blocks the write.
- **PostToolUse** (Write|Edit) — re-validates after the write (catches drift).
- **SessionStart** — injects the vault pointer so every session knows the vault exists and how to use it.

A fourth, non-blocking **SessionEnd** hook nudges the agent to capture any generalizable learning before the session ends.

The validator (the plugin's `scripts/vault/validate.mjs`) runs four gates: schema (required fields, enums), structural (id matches filename, no nested relation maps), graph (relation targets resolve), and index-drift (every node appears in the index).

Hard violations block; soft warnings inform. The validator fails safe: if it crashes, it exits 0 and lets the write through.

### Staleness: the threshold and the cohort

`updated` older than `STALE_AFTER_DAYS` (120) is a soft warning. Know what it cannot catch. An absolute threshold only fires on a node nobody touched for four months, and the nodes that rot hardest are not the ones nobody touched — they are the ones seeded together in a project's first week, describing a scaffold that has since been rebuilt three times. Measured on a real 152-node vault: zero nodes over the threshold, oldest node 45 days, and a 16-node first-week cohort describing a shape that no longer existed. The gate could not fire, and the rot was in the cohort it could not see. Nodes that get edited are the accurate ones, so the threshold is structurally aimed at the wrong stratum.

The instrument that does aim at it is a **cohort**: sort every node by `updated`, take the oldest decile (floor of 5 nodes, and skip the report entirely on a vault smaller than twice that floor — a 5-node vault would report itself), and treat that slice as the re-verification queue. Not a per-node warning: on a 152-node vault that is 16 permanent soft lines on every lint, forever, for nodes that are not individually known to be wrong — the decorative warning that gets the whole gate switched off. It belongs in `/vault-status`, the command an operator runs deliberately, as one block of text that never touches an exit code.

Not yet mechanised: no code computes this cohort today, so run it by eye — sort by `updated`, take the oldest tenth, re-read those nodes against the code — until `stalestCohort` lands in `scripts/vault/status.mjs`.

Keep the 120-day threshold either way. It costs nothing and it protects a vault that eventually runs long; it is simply not the whole answer, because a coherent cohort seeded on one day sits far inside the threshold and stays there.

## 7. Authoring workflow

1. Use `/vault-new <type> "<title>"` to scaffold a node, or the `vault-author` skill to author one with full frontmatter.
2. Fill the body sections from the template.
3. Save — the PreToolUse hook validates it.
4. Run `/vault-map` to regenerate indexes.
5. Run `/vault-lint` before finishing.

When you learn something generalizable about *how* to build or document (not project facts), capture it with `/vault-learn`; harvest those learnings into the plugin with `/vault-learnings` → `/vault-evolve`.

## 8. Design principles

- **Typed over freeform** — every node has a type and obeys a contract.
- **Generated indexes** — navigation scales without manual upkeep.
- **Provenance tracked** — every claim is `verified`, `extracted`, `inferred`, or `ambiguous`. `verified` means someone opened the code and saw it, not that a test was green.
- **Enforced, not suggested** — hooks make the contract non-optional.
- **Compounding** — every task ends with a vault update; an unindexed fact is invisible next session.
- **Self-improving** — the tooling learns from each deployment via the capture-and-harvest loop.
